# Attachments API migration (`@traceai/fi-core/attachments`)

The streaming, recording and import work changed a few behaviours that integrations built against the first attachment runtime depend on. Earlier, some of these changes broke callers silently: capture just stopped. Each one now fails loudly, as a compile error, a one-time process warning with a stable code, or an explicit reason at the call. This page lists each change and what to do about it.

| Change | Old | New | How it fails now | What to change |
|---|---|---|---|---|
| Ready state | `status().state === "queued"` | `status().state === "ready"` | TypeScript: TS2367 on any comparison with `"queued"`. JavaScript: the comparison is always false, so check for `"ready"`. | Compare with `"ready"`. Admission results (`handle.admission`, `ticket.reason`, `writer.reason`) still use `"queued"` for "admitted". |
| Completion `failed` | `completion.status === "failed"` | `"incomplete"` (transport or unknown) or `"unsupported_version"` (invalid response shape) | TypeScript: TS2367. `failed` is no longer in `AttachmentCompletion`. | Treat any status other than `validating` / `importing` as not delivered. A legacy transport that still throws `AttachmentTransportError("failed")` is mapped to `incomplete`. |
| Four-method transport (`bootstrap` / `initialize` / `upload` / `complete`) | Full support | Adapted, with reduced capability | Warns once per process: `DeprecationWarning` code `FI_ATTACHMENTS_LEGACY_TRANSPORT`. `startRecording`, WAV-tier `attachOwnedRecording` and `importCompletedRecording` return `unsupported_version` at the call, so no bytes are buffered or uploaded. Sessions cannot renew, so capture reports `expired` after the first session lifetime. | Pass `createAttachmentHttpTransportV1(...)` or implement `AttachmentTransportV1`. A wrapper around `createAttachmentHttpTransport(...)` must forward its `[ATTACHMENT_TRANSPORT_V1]` member, or wrap the V1 surface directly. Otherwise the wrapper silently becomes legacy. |
| Strict F01 response shapes | Lenient | Every response is checked against F01 (for example, status bodies need `reason`) | The affected attachment reports `unsupported_version`, and a warning with code `FI_ATTACHMENTS_WIRE_REJECTED` names the shape once, such as `UploadStatus` or `AttachmentSession`. The warning contains no values. | Make the server or test double match `spec/attachments/v1`. |
| Session renewal triggers | Only admission calls (`preflight`, `attach`, ...) | Also `status()`, `flush()`, worker wake and recording writes (design 3.1) | Not an error. HTTP doubles that mint short sessions see an extra `POST /tracer/v1/attachment-sessions` with `Idempotency-Key: bs-{session}-{n}` near expiry. | Mint sessions of one hour or more in doubles, or expect the renewal request. |
| `manager.correlation(span)` | Stamped `fi.attachment.*` on the span | Returns a snapshot only. Stamping happens when a capture is admitted (design 0.8). | Not an error: a span without an admitted capture carries no attachment attributes, which is intended. | Pass the correlation (or the span) to `attach` / `preflight` / `startRecording`. Do not rely on `correlation()` alone to mark a span. |

## Warnings

Both warning codes are exported as `ATTACHMENT_WARNING_LEGACY_TRANSPORT` and `ATTACHMENT_WARNING_WIRE_REJECTED`. On Node they go through `process.emitWarning`, so `--no-deprecation` and `--no-warnings` apply. In browsers they go to `console.warn`. Each is emitted at most once per process, per code and shape.
